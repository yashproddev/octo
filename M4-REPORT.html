Two rules that shaped everything else

Reconciliation is deterministic

No model sits anywhere in the verdict path. The same data with the same tolerances always produces the same result. That is what makes a human sign-off meaningful — a reviewer is confirming a reproducible finding, not arguing with a black box. It also means every exception can state its arithmetic: “Invoice quantity 50 exceeds GRN quantity 48 by 2 (4.1667%), outside the 0-unit / 0% tolerance.”

The system's verdict is never overwritten

system_status is written once by the engine and never updated. Human outcomes are appended to decision_log, and current_status is derived from the newest one. The machine's original judgment stays recoverable no matter how many times a person overturns it — the requirement is a structural property of the schema, not a convention someone has to remember.

Judgment calls worth knowing about

Duplicate detection keys on (vendor, invoice_number, item). The same invoice number across different items is a normal multi-line invoice. Keying on invoice number alone would have flagged every multi-line invoice in a real file as a duplicate — false exceptions on day one, and a reviewer who stops trusting the tool.

A skipped check downgrades to REVIEW, never MATCHED. If the file carries no tax column, tax cannot be verified. Reporting that line as a clean match would quietly overstate assurance; “we could not check this” and “this is correct” are different claims.

Money and quantities are Numeric, never Float. The engine compares values within tolerances, and binary floating point would manufacture variances that do not exist in the source data — phantom mismatches a human then has to adjudicate. There is a test pinning this.

Canonical records are scoped to their ingestion run. purchase_orders is unique on (ingestion_run_id, po_number), not po_number alone. Re-uploading the same file produces a separate, independent run rather than a primary-key collision.

Section 3Known limitations

Platform ceilings
  • 4.5 MB upload cap — a hard Vercel request-body limit, roughly 25–40k rows. Larger files must be split into separate runs.
  • 60-second function timeout. Comfortable at prototype volumes; a genuinely large file would need a queue.
  • Numeric ceiling of 99,999,999,999,999.9999 per value. Now caught during validation with a clear message — it previously surfaced as an opaque HTTP 500.
  • Cold starts. pandas and numpy make the function bundle large; first request after idle is slow.
Deliberate scope exclusions
  • No authentication. The acting user is an X-Actor header from a UI field, trivially spoofed. Adequate for a prototype, unacceptable for real audit.
  • No cross-run duplicate detection. The same invoice billed in two separate uploads is not flagged. The schema supports it; the rule does not yet.
  • No fuzzy matching. Vendor and item names are normalised for case, punctuation and whitespace only. “Acme Ltd” and “Acme Limited” are different vendors.
  • GRN references are synthesised. The CSV carries no GRN number, so one header is generated per PO per run.
  • Tax uses a single configured rate (18% default) for every line. Mixed-rate invoices will misreport.
  • Currency is captured, never converted. A multi-currency file reconciles numerically without regard to currency.
  • No editing after normalization — correcting data means re-uploading.
Operational risks to close before real use
  • Credentials were shared in plaintext during this build. The Neon password and the Vercel token should both be rotated.
  • Dev and production share one database. Neon branching should separate them before anyone else starts using the app.
  • The deployment is publicly accessible by request — anyone with the link can upload data and record decisions.
  • Tests run against the live database. They are transaction-wrapped and roll back, but they are not isolated from production data.

Where a model could legitimately be added

The reconciliation path should stay deterministic permanently — that property is what makes the audit trail defensible. There are two places a model could help without touching it:

  • Column-mapping fallback. When a header matches no alias, a model proposes the canonical field. The deterministic dictionary still wins; the model only sees the unmatched remainder, and its output is a suggestion the user confirms. This attacks the most likely reason a demo stalls — a CSV with headers nobody anticipated.
  • Exception narration. Prose over the templated findings. Presentation only; the stored explanation remains authoritative.

Neither is built. The first is worth having; the second is decoration over text that already reads well.

Section 5Connecting M4 to the larger MRO platform

The prototype was built so that this is an integration exercise rather than a rewrite. One constraint carried the weight: nothing in app/modules/m4/ imports FastAPI. The engine, the column resolver, the validator, the normalizer and the decision service are all plain Python over SQLAlchemy sessions. The HTTP routes are a thin skin over them.

Four integration seams, easiest first

1 · Lift the module. Copy app/modules/m4/ into the platform, point it at the platform's session factory, and call ingest_csv, normalize_run, reconcile and record_decision directly. No HTTP involved. This works today.

2 · Replace CSV ingestion with live data. Ingestion is the only part that assumes a file. Everything downstream operates on staging_records — rows of mapped JSON. A platform feed writing into that table gets the whole engine for free, because normalization and reconciliation never learn where the rows came from.

3 · Adopt the platform's canonical records. M4 currently scopes vendors, POs, GRNs and invoices to an ingestion run because it has no master data. Where the platform already owns those entities, the run-scoped tables become views onto the platform's, and the unique constraints move from (ingestion_run_id, po_number) to the platform's own identity. The reconciliation tables are unaffected — they reference line IDs, not the scoping.

4 · Federate the audit trail. decision_log is append-only with actor, timestamp, rule version and before/after status. It is shaped to merge into a platform-wide audit stream; swapping the X-Actor header for real identity is the only change required.

What M4 gives the wider platform

Beyond closing invoices, M4 produces the verified trade record the rest of the OctoProc thesis depends on: a PO, a goods receipt and an invoice that have been checked against each other, with every exception explained and every closure attributable to a named decision. That artefact is what makes downstream supply-chain finance underwritable — a lender needs evidence that a real transaction happened, and this is the module that produces it.
